## 1. Summary of AI Prompts Used
Throughout the project lifecycle, AI was utilized as a drafting assistant for structural alignment:
- **Prompt P1:** Requirements classification (Functional vs Non-functional).
- **Prompt P2 & P3:** Use Cases text generation and Mermaid flowchart syntax for Use Case diagrams.
- **Prompt P4:** Candidate classes identification (Explicit, Inferred, Rejected) with evidence mapping.
- **Prompt P5 & P6:** Mermaid Class Diagram and Sequence Diagram syntax generation.
- **Prompt P7:** Python implementation (`main.py`) translating UML design classes and sequence logic.

## 2. AI Mistakes & How We Caught Them (Critical Review)

As required, we critically reviewed every output generated by the AI instead of blind acceptance. Below are the key mistakes made by the AI and how our team corrected them:

### 🟥 Mistake 1: Missing Constraint Enforcement for R4 (Max Upcoming Appointments)
- **What the AI said:** The AI initially generated a generic `Patient.book_appointment()` method that simply added any appointment to a list without checking any numerical limits, violating Requirement R4.
- **Why it was wrong:** R4 explicitly states that *a patient can have at most N upcoming appointments at any given time*. Without a validation check, a patient could theoretically spam infinite bookings.
- **How we noticed & fixed it:** During our class diagram and sequence review, we checked the OCL constraint `{self.appointments->select(...)->size() <= N}`. We instructed the AI to rewrite the `book_appointment` method inside the `Patient` class to explicitly count active (`Pending` or `Accepted`) appointments and reject bookings if the count reaches $N$.

### 🟥 Mistake 2: Incorrect Multiplicity and Object Composition in Class Diagram
- **What the AI said:** In the first draft of the class diagram, the AI made `Appointment` and `TimeSlot` a loose bidirectional association rather than enforcing a strict reservation check, and allowed doctors to hold conflicting overlapping slots.
- **Why it was wrong:** Logically, a time slot must be marked unavailable (`is_available = False`) the exact moment an appointment successfully reserves it, preventing double-booking.
- **How we noticed & fixed it:** We cross-referenced the class diagram with the sequence diagram steps for `UC-02 (Book an Appointment)`. We modified the `TimeSlot.reserve()` method in Python to change the slot state safely upon booking and updated the multiplicity logic.

### 🟥 Mistake 3: Missing State Recovery on Doctor Rejection (R3)
- **What the AI said:** When designing the `Doctor.decline_appointment()` logic, the AI marked the status as `Declined` but forgot to make the associated `TimeSlot` available again for other patients.
- **Why it was wrong:** If a doctor declines an appointment, that specific time slot remains locked forever in memory, which breaks clinic scheduling workflows.
- **How we noticed & fixed it:** We traced the alternative flow of `UC-03` and realized the slot needed recovery. We manually added `appointment.time_slot.is_available = True` inside `decline_appointment()`.
